Where the message starts

Upstream BFSI applications — core banking, payments, and loan origination systems — generate the transactions that eventually need to reach downstream systems reliably, in order, and without loss. Nothing downstream matters if this handoff isn't trustworthy, which is why the very first hop is into a queue manager rather than a direct point-to-point call.

IBM MQ — the message broker

This is where I spend most of my production hours. I design, configure, and administer Queue Managers, Channels, Listeners, and Clusters across Dev, Test, UAT, Pre-Prod, DR, and Production landscapes — Local, Remote, Alias, and Transmission Queues, plus Topics and Subscriptions for pub/sub patterns.

High availability comes from Multi-Instance Queue Managers, MQ Clustering, and active-standby failover, engineered to meet enterprise RTO/RPO targets. Security is enforced through SSL/TLS channel encryption, PKI keystore/truststore management, CHLAUTH rules, and Object Authority Manager (OAM) permissions. When something breaks — queue buildup, DLQ growth, backout queues, channel failures, certificate expiry — this is also where the troubleshooting, batch reprocessing, and recovery happens, with zero business data loss as the standard.

Queue ManagersClusteringCHLAUTHSSL/TLS · PKIDLQ / Backout Queues

IBM ACE / IIB — transformation & routing

Once a message is safely queued, IBM App Connect Enterprise v12 and IBM Integration Bus v10 do the transformation work: message flows built from ESQL, Java Compute Nodes, Mapping Nodes, and shared reusable libraries, with exception-handling frameworks so failures are caught, not silently dropped.

Payloads move between JSON, XML, XSD, DFDL, and XSLT/XPath depending on what the consuming system expects, and the same flows expose REST and SOAP endpoints alongside JMS-based messaging. Deployment is BAR-file packaging through Jenkins CI/CD, promoted DEV → TEST → UAT → PROD with SonarQube quality gates and rollback plans, not manual copy-paste.

ESQLJava Compute NodeDFDL / XSLTREST · SOAP · JMSBAR Deployment

Apache Kafka — event streaming

Not every consumer wants a queued, transactional message — some want a continuous, replayable event stream. That's where MQ-to-Kafka bridging comes in (the dashed violet path above): production data moving out of the transactional MQ world into topics and partitions for real-time ingestion by analytics and event-driven services, without the source systems ever knowing Kafka exists downstream.

Topics & PartitionsMQ-Kafka BridgingEvent-Driven Architecture
